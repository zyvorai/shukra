Rules, alerts, state and the API

Detection is one YAML file. Alerts leave through sinks you choose. State survives a restart with a data directory. Everything the console shows is a plain API call: 38 routes in all.

Detection rules

One file (-watchlist), re-read on systemctl reload shukra and checked offline with shukractl rules check. A bad file keeps the previous rules.

destinations:  # out to, or in from
  - {cidr: 185.0.0.0/8, name: egress, severity: high}
dns:           # a name the guest looked up
  - {name: pool, suffix: nanopool.org}
tls:           # a server name in a ClientHello
  - {name: tor, suffix: torproject.org}
thresholds:    # a per-VM metric over a window
  - {name: slow, metric: block_write_p99_ms, value: 50}
responses:     # off unless present
  - {name: contain, rules: [pool], action: isolate}

A detection keeps the attribution of the event that caused it. A rule says nothing until a full window of history exists. Or add a baselines: section and let each VM teach it what is normal. vmm: is optional: the tripwires need no section. responses defaults to propose.

Alert sinks

A signed webhook (HMAC, when a secret is set), syslog and a JSONL file.

Deploy, requirements, and how it is tested

Shukra is a systemd unit on the hypervisor, not a Helm chart, because eBPF has to run where the VMs run. One script installs it; a tarball and a .deb cover hosts without a compiler.

Install

$ ./scripts/deploy-remote.sh 10.0.1.5 sus
# build on the host, install, start
# shukra.service on :30970, run doctor
$ make dist
# tarball and .deb (amd64, arm64)

Keys and extra flags go in /etc/shukra/env (mode 0600). Rules are read from /etc/shukra/detections.yaml and state is kept in /var/lib/shukra.

Before a host is reachable: the API key is the admin key. The shipped unit listens on 0.0.0.0:30970 over plain HTTP, so the key crosses the network in clear: pass -tls-cert and -tls-key, bind to a management address, or firewall the port. A daemon started with no SHUKRA_API_KEY uses the dev token shukra. A fresh install generates a random key, but an install over an older deploy keeps the key it finds, so an old host may still run the dev key. shukractl doctor fails it on a non-loopback address.
Isolation, an enforcing policy and a response need -isolate-allow. Without a management allow list each is refused, so a VM you cut off can still be reached by you.

Tested for real, not just unit-tested

EVERY PUSH AND PR

Go tests (545 test functions), the console's 56 tests and build, the programs loaded into the runner's kernel, the egress policy checked packet by packet, the installer.

REAL KERNEL, TAP RIG

Guest traffic, isolation, drops, every handshake outcome, DNS and TLS names, egress policy and VMM tripwires, in a network namespace with a real veth.

REAL KVM GUESTS

Two guests booted by fluxvm on a runner with /dev/kvm: events attributed, packet counts equal the kernel's, an audit policy marks exactly what is outside its list. A real QEMU, asked over QMP to open /etc/shadow, raises a critical vmm-sensitive-open (58 of 58 checks on the reference hypervisor).

Exact, not approximate. On GitHub's kernel, 17 outbound attempts came out as 5 accepted, 6 refused, 4 never answered and 2 blocked, with 1 retransmit, and attempts = accepted + refused + never answered + blocked held. Isolation and an enforcing policy are shown to survive kill -9, a restart and a graceful stop, and to be lifted by -detach-all.

Release

A v* tag builds the tarball and .deb for amd64 and arm64. There is no tagged release yet: the changelog lists what has merged to main.

Honest limits. The live-guest test fails, rather than skips, with no KVM. A SYN is "never answered" after 3 seconds; in a SYN flood the oldest pending entries are forgotten uncounted.

Where Shukra fits, and a buying checklist

Shukra is one Zyvor product, open source, and it works alone. What it does not do is stated here so the choice is clear.

What Shukra is

Runtime intelligence and security for KVM from the hypervisor: what a host measures about its VMs, what became of a guest's connections, what a VMM opens, and ways to hold a VM to a policy or cut it off. Guests untouched.

What it is not

Not an agent in the guest, so it cannot name a process inside one. Not a firewall: isolation and an egress policy act on one VM's tap, and a policy judges networks a VM starts connections to, not ports. Not a CNI. Not a sandbox for the VMM: a tripwire reports.

FluxVM

Recognised: QEMU, Cloud Hypervisor, Firecracker and fluxvm-hypervisor guests are named from FluxVM's own record and traced on their host veth.

PacketWolf and Zeus OS

The intended consumers of Shukra's JSON. They are not in this repository, and nothing here depends on them.

Buying checklist

  1. Run shukractl doctor on a candidate hypervisor: exposure, what is attached, what it cannot see, each finding with a fix.
  2. Start observe-only. Read Overview, Programs and one real slow VM's Explain. Nothing is dropped.
  3. Check the kernel: 5.17 for drops, 6.6 for the tap, egress policy and isolation. Read what each host reports as detached, and why.
  4. Write a small rules file (add baselines: for first sightings), check it with shukractl rules check, and wire one alert sink. Give Prometheus the read-only key.
  5. Set a real API key, and TLS or a management address, before any non-lab host is reachable. Check older deploys for the dev key.
  6. Rehearse isolate on a test VM with an allow list: confirm it is refused without one, survives a daemon restart, and releases.
  7. Try an egress policy on one VM: learn, audit for a day, then enforce with --confirm and let one run out to watch it revert. Turn a response on as dry_run or propose, read the bundle before approving, and list your primary databases in never_isolate.
  8. Run a day with a data directory, then ask explain --at and incident about a past time. Read the resolution line. Read the "neither" figure of shukractl advise before trusting an over-provisioned verdict.
  9. Decide whether PacketWolf or Zeus OS will consume the JSON, and which key they get.
