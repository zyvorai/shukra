Rules, alerts, state and the API

Detection is one YAML file. Alerts leave through sinks you choose. State survives a restart when you give the daemon a directory. Everything an operator sees in the console is a plain API call.

Detection rules

One file (-watchlist), re-read on systemctl reload shukra and checked offline with shukractl rules check. A bad file keeps the previous rules.

destinations:  # out to, or in from
  - {cidr: 185.0.0.0/8, name: egress, severity: high}
ports:
  - {port: 22, name: ssh-in, dir: in}
dns:           # a name the guest looked up
  - {name: pool, suffix: nanopool.org}
thresholds:    # a per-VM metric over a window
  - {name: slow-disk, metric: block_write_p99_ms, value: 50}

A detection keeps the attribution of the event that caused it. A rule says nothing until a full window of history exists. Or add a baselines: section and let each VM teach it what is normal.

Alert sinks

  • Signed webhook: HMAC-signed when a secret is set.
  • Syslog and a JSONL file.

Deploy, requirements, and how it is tested

Shukra is a systemd unit on the hypervisor, not a Helm chart, because eBPF has to run where the VMs run. One script installs it; a tarball and a .deb cover hosts without a compiler.

Install

$ ./scripts/deploy-remote.sh 10.0.1.5 sus
# build on the host, install, start
# shukra.service on :30970, run doctor
$ make dist
# tarball and .deb (amd64, arm64)

Set a real key on any host that is not a lab. Without SHUKRA_API_KEY the daemon uses a dev token and says so, and doctor reports it as a failure on a non-loopback address.

Tested for real, not just unit-tested

EVERY PUSH AND PULL REQUEST

Go tests (366 test functions), the console's 45 tests and its build, the programs loaded into the runner's kernel, the installer.

REAL KERNEL, TAP RIG

Guest traffic, isolation, drops and every handshake outcome, in a network namespace with a real veth, with exact counts.

REAL KVM GUESTS

Two guests booted by fluxvm on a runner with /dev/kvm: guest events are attributed, packet counts equal the kernel's, taps come off when the VMs go.

Exact, not approximate. On GitHub's kernel, 17 outbound attempts came out as 5 accepted, 6 refused, 4 never answered and 2 blocked, with 1 retransmit, and attempts = accepted + refused + never answered + blocked held. Isolation is shown to survive kill -9, a restart and a graceful stop, and to be lifted by -detach-all.

Release

Pushing a v* tag builds the tarball and .deb for amd64 and arm64. Shukra has no tagged release yet: the changelog lists what has merged to main.

Honest limits. The live-guest test fails, rather than skips, on a runner with no KVM. A SYN is judged "never answered" after 3 seconds, and under a SYN flood the oldest pending entries are forgotten uncounted (attempts still counts every one).

Where Shukra fits, and a buying checklist

Shukra is one Zyvor product, open source, and it works alone. What it does not do is stated here so the choice is clear.

What Shukra is

Runtime intelligence and security for KVM from the hypervisor: what a host measures about its VMs, what became of a guest's connections, and a way to cut a VM off. Guests untouched.

What it is not

Not an agent in the guest, so it cannot name a process inside one. Not a network firewall: isolation is one VM's tap, with an allow list. Not a CNI or a network policy engine: it sits on the hypervisor.

FluxVM

Recognised: QEMU, Cloud Hypervisor, Firecracker and fluxvm-hypervisor guests are named from FluxVM's own record and traced on their host veth.

PacketWolf and Zeus OS

The intended consumers of Shukra's JSON. They are not in this repository, and nothing here depends on them.

Buying checklist

  1. Run shukractl doctor on a candidate hypervisor: exposure, what is attached, what it cannot see, each finding with a fix.
  2. Start observe-only. Read Overview, Programs and one real slow VM's Explain. Nothing is dropped.
  3. Check what the kernel supports: 5.17 for drops, 6.6 for the tap and isolation. Read what each host reports as detached, and why.
  4. Write a small rules file (add a baselines: section if you want first sightings reported), check it offline with shukractl rules check, and wire one alert sink. Give Prometheus the read-only key.
  5. Set a real API key and TLS before any non-lab host is reachable.
  6. Rehearse isolate on a test VM with an allow list: confirm it is refused without one, survives a daemon restart, and releases.
  7. Run a day with a data directory, then ask explain --at and incident about a past time. Read the resolution line.
  8. Run shukractl advise and read the "neither" figure before trusting an over-provisioned verdict; it is advice, and a person decides.
  9. Decide whether PacketWolf or Zeus OS will consume the JSON, and which key they get.
