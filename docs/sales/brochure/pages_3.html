Lost traffic, then contain

Another ticket: api-01 cannot reach a service. Is the destination refusing, is something dropping the packets, is the guest not reading its NIC, or is Shukra itself in the way? The tap answers each connection, and the kernel names each drop.

What the kernel dropped, and why

Reason on the tapWhat it meansWhere to look
TC_INGRESS, TC_EGRESSa tc or TCX program on the tap dropped a frame; if Shukra accounts for it, that was isolationbpftool net show dev <tap>: another program (Cilium, a tc filter)
FULL_RINGthe tap's queue is full: the guest is stalled, has no working NIC driver, or is overloadedthe VM itself

QDISC_DROP, CPU_BACKLOGthe host's own queues are overflowinghost load and qdisc settings

Each drop is also attributed to the function that freed the packet. Shukra's own isolation drops are subtracted, so "is it us?" has an answer: shukractl trace drops. Reason names are read from the running kernel's BTF and never hard-coded; one it cannot name is shown as reason N, not guessed.

1
Read the outcome. shukractl trace tap --vm api-01 shows accepted, refused, never answered and blocked per direction, with the guest's handshake time.
2
Read the drops. shukractl trace drops --vm api-01 says what the host kernel dropped on the tap, by reason and function, and whether it was Shukra.
3
If the VM must be cut off, shukractl isolate api-01 drops its tap traffic except your management network. It prints whether the kernel took the change.
Isolation is real, and conditional. It needs an explicit allow list (-isolate-allow) and Linux 6.6 or newer, and is refused without them, because a VM that could reach nothing could not be reached by the host that isolated it. applied is true only after the kernel took the change on every tap; a half-applied isolation is reported partial, not silently reopened. It blocks the VM's tap: it does not touch vhost-user or SR-IOV interfaces.

What Shukra reads, and what it never does

The accurate promise is stronger than "no agent": nothing runs inside a guest, no application data is read, and the one thing read beyond headers is stated here, can be turned off, and is bounded.

By default

Metadata only. Counters and histograms from the host: exits, scheduling, block requests, TCP connects, tap packet counts. From a tap: headers, so flow addresses and ports, handshake outcomes and kernel drop reasons. VM names from the QEMU command line.

One bounded exception

DNS names. For a plain DNS query on UDP port 53, the first question (at most 128 bytes: the name and the type). -dns-events=false turns it off. Answers, DNS over TCP, TLS and HTTPS are not read.

Never

Anything inside a guest. Application payloads. The guest's own steal counter. Which process in the guest made a connection. Keys in any API response, in doctor or in systemctl show.

QuestionAnswer
Does anything run inside the VM?No. There is no agent. Everything is read from the host: /proc, kernel tracepoints, and the host side of each VM's tap.
Are host TCP events the guest's?No. Host connects are the QEMU process's own sockets, labelled qemu-process and guest_attributed: false. Only events seen on a VM's tap are guest-tap and guest-attributed, and only for a tap that belongs to a VM in the current scan. A tap no VM owns stays unattributed.
Can a guest change what is attributed to it?No. Attribution comes from the tap's owner, found on the host, not from anything in a packet.
Can a hostile guest hurt the daemon?It can generate load, not growth. Tables keyed by packet contents are fixed-size LRUs; events from a tap are rate-limited to 200 per second; DNS names are cut at 253 bytes with every non-printable byte replaced, so a name cannot carry an escape sequence into a log.
Who can isolate a VM?The admin key only. A separate read-only key reads everything, including /metrics and the stream, and cannot isolate or release. Give that one to Prometheus.
What does an incident bundle expose?VM names, addresses and DNS names, as the event list does. It holds nothing from the daemon's configuration except the allow list. It is written with mode 0600.
What does the daemon need to run?Root with six capabilities and a read-only filesystem apart from its data directory (0700). CAP_SYS_PTRACE and CAP_DAC_READ_SEARCH are used only to read a libvirt VM's tap names from /proc/<pid>/fd; drop them if you run no libvirt VMs.
What this release will not pretend. It can say which VM and which address, not which process inside the guest. A VM with user-mode networking has no tap and so no guest traffic, and shukractl doctor names it. The scheduler program records the command name of a host task that took a vCPU's CPU, so names like kubectl can appear in the API. Treat the data directory as sensitive, and alert sinks as a place that data leaves the host.
