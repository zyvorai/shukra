# Shukra 0.1.0

This note describes the first packaged release. It is not a tag. Tag `v0.1.0` only when you mean to publish the artifacts.

## Kernel matrix

| Host | What runs |
|---|---|
| Linux 5.8 and newer | Host probes: `kvm`, `sched`, `block`, `net`, `vmm` |
| Linux 6.6 and newer | Guest tap traffic, isolation, and egress policy on TCX |
| Older than 6.6, with clsact | The same guest programs on a sched_cls filter at priority 50. A pass is `TC_ACT_PIPE`, so the next filter on the tap still runs. A drop does not |
| Neither hook attaches | Host-only. `shukractl doctor` says coverage is host-only |

`scripts/test-tap.sh` covers the TCX path and, with `SHUKRA_FORCE_TC=1`, the classic filter beside a later one.

## Upgrade

Hosts that reached `0.0.0.0:30970` over plain HTTP stop doing that. The unit listens on `127.0.0.1:30970`. To keep the old bind, set both `-listen 0.0.0.0:30970` and `-allow-insecure-http` in `SHUKRA_EXTRA_ARGS`, or terminate TLS in front of loopback. A packaged install keeps the random key in `/etc/shukra`. `/etc/shukra` and `/var/lib/shukra` are not removed.

A new tap is attached from a netlink notification, and its saved policy is pushed before the daemon reports that tap as covered. The two-second scan remains. `-quarantine-uncovered` is off: an enforcing VM with a live tap and no program is a `tap-uncovered` detection, not a blackhole.

## Rollback

Install the previous `.deb` with `dpkg -i`. Configuration and state stay. If a classic filter was left behind, `shukrad -detach-all` removes Shukra's filters and a clsact qdisc only when this install created it and nothing else remains.

## Known limitations

Copied from the product limits, plus what this release still does not do:

- No guest agent, and no view of which process inside the guest.
- VLAN tags, IPv6 extension headers, ICMP events, and memory pressure are not measured.
- A tap that is not in the host namespace, and that nothing maps to one, has no guest traffic.
- Responses only isolate, and only when you turn them on. An egress policy is not a firewall.
- Enforcement across a restart needs `/sys/fs/bpf`.
- Percentiles come from log2 buckets and can read up to 2x high.
- There is no fleet controller, no migration timeline, and no language model in the daemon.
